# Wakes: a thread that comes back by itself

**Status:** proposal (14 Nov 2026). Step 2 of
[scheduled turns](2026-11-03-scheduled-turns.md); a piece of roadmap item 11,
*Routines from the phone*. From agent mail #439 (the host-setup session),
passing on David's ask: "could we add that kind of resuming functionality to
agent-media as a distributable feature... Maybe even a kind of generic
feature like the heartbeat feature that openclaw uses", then "Yes, please".

## Why

red2 was rebooted twice on 14 Nov, and both times the host-setup session
asked David to resume its thread by hand. That session wrote
`agent-resume-after-boot` (agent-config 1837117): a session queues itself, a
user unit runs `media session send <id>` 30 s after boot, and entries older
than 6 h are dropped. It works, but it lives in one host's config, and it is
the third shape of the same idea: `media session wake` on a host timer
(step 1), the app's `remind 2h` action, and the shell polling loops sessions
write when they want to look again at CI or a download ("no silent waits").

## One primitive: a wake

A wake is **a message for a thread, and when to send it**:

| field | |
|---|---|
| `target` | a session id, or a folder (as `media session wake`: its live session, else a new one) |
| `message` | what the agent is told; an order file (`--order`) is read at firing time |
| `when` | `boot` · `at 07:30` · `every 2h` · `on <event>` |
| `from` | who set it (`self`, `david`, `schedule`, a session id) |
| `expires` | a wake older than this is dropped, not fired (default 6 h for `boot`, none for `every`) |
| `persona`, `permissions` | as `wake` today |

Firing a wake is `media session wake`/`send` and nothing else, so it keeps
every guard those already have: queued behind a running turn, refused while
a question or permission card is up (it tries again at the next tick, and
gives up at `expires`), held by the speech gate like any reply, started
under the folder's permission profile.

## Where it is kept, and the clock

- **Kept by sessiond, on disk** (`$XDG_STATE_HOME/agent-media/wakes.json`,
  written atomically), so wakes survive a reboot and a sessiond restart.
- **Time wakes use the scheduler we already have**
  (`agent_media_core.scheduler`), not a clock of their own and not
  generated systemd timers. The mail suggested `systemd-run --on-calendar
  ... Persistent=true`; the repo went the other way on 12 Nov
  ([fewer services](2026-11-12-fewer-services.md) §4b: 36 unit files for 18
  jobs on red5) and the scheduler already catches up like `Persistent=true`
  (a missed `at` runs once at the next start). It also works on Termux,
  where there is no systemd. Wakes become a second job source beside
  `JOBS` and `[jobs]`, listed by `media schedule list`.
- **Boot wakes fire from sessiond's own start**, once the session host is
  up and the network is (the same wait the tunnel needed, a084e080), a
  little after (30 s, so the server and the phone's worker are back too).
  A restart that sessiond drains already resumes the sessions it cut off
  (restart_services); a boot wake is for the case it cannot know about: a
  reboot, a power cut, an OOM kill.
- **Event wakes** come from the places that already know: the agent-mail
  delivery (a mail for this folder), the CI watcher (a run finished), a
  phone job or download finishing (phone_jobs), a process exiting, a URL
  answering. Each calls `wakes.fire(event, detail)`; a wake `on ci:<repo>`
  matches. Start with the three we already watch (mail, CI, downloads); the
  general "a command says yes" check is a scheduler job that runs it.

## Setting one

```
media session wake-on <id|folder> boot "Carry on with the red2 setup: step 4."
media session wake-on <id|folder> at 07:30 --order orders/morning.md
media session wake-on <id|folder> every 2h --heartbeat
media session wake-on <id|folder> on ci:agent-media "CI finished; look."
media session wakes [<id|folder>]          list, with next due
media session wakes --pause <wake> | --delete <wake>
```

- **Agents set their own**, with the CLI or an MCP tool (`wake_me`) on
  media-mcp. "Wake me when CI is done" replaces the polling loop, and
  survives the restart that a background shell loop does not (the reason
  for the "watcher outside sessiond" rule).
- **A session's own `boot` wake by default?** Not at first: a session asks
  for it when it is mid-way through something that a reboot would strand.
  Revisit once a few reboots have shown whether everything wants it.
- **The app** lists a thread's wakes in its menu (pause, delete, edit the
  time), and `[[actions: … -> remind 2h]]` becomes a wake rather than its
  own mechanism. Server routes: `GET/POST/DELETE /sessions/<id>/wakes`.

## Heartbeat

OpenClaw's idea, kept small: a recurring wake whose message is "read
`HEARTBEAT.md` in this folder and do what it says". The checklist is the
folder's, edited by David or the agent; agent-media ships none.

What stops a heartbeat becoming noise is the **quiet reply**: when there is
nothing to report, the agent ends its turn with `[[quiet]]` on its own line.
The server then keeps that turn silent: no speech, no unread mark, no push,
and the thread's list entry does not jump to the top. The turn is still in
the transcript. `[[quiet]]` is honoured only on a turn a wake started, so a
reply to David is never swallowed. The context hook's notes say when to use
it.

## Limits

- At most one firing per wake at a time; a wake whose last turn is still
  running is skipped, not queued again.
- `every` has a floor (15 min) unless set in config, so a mistaken
  `every 1m` cannot keep a model busy all day.
- A wake's message names who set it (`[Wake from <from>]`), as agent mail
  is signed, so the agent and David can see a turn was not his.
- Wakes are per host, as sessions are. A host that moves takes its
  `wakes.json` with it (a line in the machine declaration).

## Steps

1. `wakes.py` (store, fire, expire) and `boot` wakes from sessiond's start,
   with `wake-on boot` and `wakes` on the CLI. The host-setup session then
   retires `agent-resume-after-boot` or makes it a shim.
2. `at` / `every` through the scheduler; `[[quiet]]`; `--heartbeat`.
3. The MCP tool, and `on` events: mail, CI, downloads.
4. The app: a thread's wakes in its menu; `remind` becomes a wake.
